## Why it matters

Cloud platforms offer capacity on demand, managed services and fast environments for development. Banks also carry obligations that do not move to the provider: data residency, security, resilience and the ability to leave. Most banks therefore run a **hybrid** estate, keeping some systems in their own data centres and putting others in the cloud. The architecture question is which workload goes where, and how the pieces connect safely.

This page describes general patterns. It does not describe any organisation's actual estate.

## The model explained

### Three kinds of place

**On-premises** means the bank's own data centres and hardware. **Private cloud** means cloud-style automation on infrastructure dedicated to the bank, in its own premises or a provider's. **Public cloud** means shared infrastructure from a provider, rented by the hour. A **community cloud** is shared among a defined group, such as banks of one type.

### Connectivity and identity

Workloads in different places must talk to each other securely and predictably. Private, dedicated links between the bank's data centres and the cloud region carry traffic that should never cross the public internet, usually over two separate paths. **Identity federation** lets staff and services use one identity across both environments, so access is granted and removed in one place.

### Making the exit plan real

An exit plan is only useful if it can be carried out. That means knowing, for each workload, which provider-specific services it depends on and what would replace them; keeping data in formats that can be exported; and holding enough skills in-house to run the workload elsewhere. Some banks rehearse exit by periodically restoring a workload's backups into another environment and running it there. The cost of exit is lowest when it is considered at design time, before the workload has grown around one provider's features.

### Multi-cloud

Using more than one cloud provider can reduce dependence on one supplier and give a way out if a relationship ends. It also multiplies skills, tooling, security configurations and network links. Many banks use multiple providers for different workloads rather than running the same workload across several.

### Cost governance

Cloud costs grow quietly: idle environments, oversized instances, data moving between regions. Tagging every resource to an owner, setting budgets with alerts and reviewing spend regularly keep the bill tied to value.

## Failure modes

- **Accidental exposure** through a misconfigured storage bucket or network rule in the cloud.
- **Data outside approved locations,** for example backups or logs replicated to another region.
- **An exit plan that exists only on paper,** never tested and dependent on provider-specific services.
- **Hidden coupling,** where an on-premises core cannot work without a cloud service, or the reverse, making both a single point of failure.
- **Cost overruns** from resources nobody owns.

## When to use it, and when to avoid it

Use public cloud for workloads that benefit from elastic scale, such as channels, analytics and development environments, once the outsourcing, security and residency requirements are met. Keep the systems of record where the bank has the strongest control and the clearest exit path, unless a considered risk assessment says otherwise. Avoid moving a workload only because it is fashionable; move it because the gain is clear and the obligations are covered.

## Questions for a design review

- Why does this workload belong where it is placed, in one sentence a regulator would accept?
- Where will its data, backups and logs physically reside?
- Which controls are the bank's responsibility and which are the provider's?
- How would the workload leave this provider, how long would it take, and has that been tested?
- Who owns each cloud resource and its cost?
