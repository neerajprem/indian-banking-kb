## Why it matters

Payments are where banking meets the outside world in real time. A customer who taps "pay" expects an answer in seconds, and a merchant expects the money to be there. Behind that answer, several independently run systems must agree on what happened, even when a network link drops halfway through. Getting that agreement right, every time, is the core problem of payment architecture.

## The model explained

### Participants, switch and settlement

A payment system has **participants**, usually banks, and an **operator** that runs a central **switch**. The switch receives a payment message from the payer's bank, routes it to the payee's bank, collects the answer and passes it back. Smaller banks and non-bank firms often join through a **sponsor bank** that is a direct member and settles on their behalf.

Moving the message is only half the job. **Settlement** moves the money between banks, in the accounts they hold at the central bank. Some systems settle each payment on its own; others settle the net amount each bank owes at intervals.

### Message standards

Messages follow published formats so that every participant can read them. Card and ATM networks have long used ISO 8583, a compact format built for authorisations. ISO 20022 is a richer, structured format increasingly used for high-value and cross-border payments, because it carries more information about the payer, the payee and the purpose. UPI defines its own interface specifications, which banks and apps must implement and certify against.

### Every payment is a state machine

A payment moves through a small number of states and must end in exactly one final state. The difficult cases are the ones in the middle: the payer has been debited but no answer has come back from the payee's bank.

### Idempotency: the same request twice must do nothing new

Networks fail, so senders retry. If a retry is processed as a new payment, the customer pays twice. Every payment therefore carries a unique reference created by the sender, and every system in the chain records references it has already handled. A repeat with a known reference returns the original answer instead of moving money again. The same reference lets any party ask later, "what happened to this payment?", and get one consistent answer.

### Reversals, disputes and reconciliation

A pending payment is resolved either by confirming the credit or by reversing the debit. At the end of each cycle, every bank compares its own records with the operator's settlement report. Any mismatch becomes an exception to investigate. Disputes, such as a customer saying goods never arrived, follow a separate, slower process with its own rules and deadlines.

## Failure modes

- **Duplicate payments** when a retry is treated as new because references are missing or not checked.
- **Stuck payments** that stay pending because no job asks for their status or reverses them in time.
- **Reconciliation breaks** when a bank's records and the operator's report disagree and no one owns the difference.
- **Sponsor-bank bottlenecks** when many smaller participants depend on one direct member's systems.

## When to use it, and when to avoid it

Use this model, a central switch with a state machine per payment, for any system where many independent parties must agree on money. Avoid building a private payment network where a public rail already does the job; joining the existing rail is usually cheaper and safer. Inside a bank, avoid letting each channel talk to each rail directly. A single payment hub that owns references, states and reconciliation is easier to control.

## Questions for a design review

- Where is the unique reference created, and does every retry reuse it?
- Which component owns each payment's state, and can it answer a status query at any time?
- How are pending payments found and resolved inside the regulator's time limits?
- What does reconciliation compare, how often, and who owns each exception?
- What happens to in-flight payments if the switch connection drops?
