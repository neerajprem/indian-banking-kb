## Why it matters

Banks are attractive targets because they hold money and personal data, and because their systems connect to thousands of others. Security architecture decides how far an attacker can get after the first mistake: a phished password, an unpatched server, a misconfigured cloud bucket. The goal is not a system that can never be breached, but one where a breach is contained, detected quickly and reported properly.

This page describes principles and common patterns only. It does not describe any organisation's actual controls.

## The model explained

### Defence in depth and zones

**Defence in depth** stacks independent controls so that each failure is caught by the next layer. The network is split into **zones** by trust level, and traffic between zones passes through controlled points. The most sensitive systems, such as the core ledger and the systems that handle keys and PINs, sit in the innermost zone and accept connections only from specific systems in the zone next to them.

### Card data scope

Systems that store, process or transmit card numbers fall under strict card-industry security rules. Architects shrink that **scope** by keeping card data in as few systems as possible and replacing it with tokens everywhere else, so most of the estate never sees a real card number.

### Hardware security modules

A **hardware security module** (HSM) is a tamper-resistant device that stores cryptographic keys and performs operations with them, such as verifying a PIN or signing a message, without ever revealing the key. Payment PINs are checked inside HSMs, so no application server ever holds a PIN in clear text.

### Privileged access, just in time

Administrator accounts can change anything, so they are the most valuable thing an attacker can steal. **Privileged access management** (PAM) keeps those credentials in a vault, grants access through a controlled gateway and records every session. **Just-in-time access** goes further: nobody holds standing administrator rights, and access is granted for a specific task, approved, time-limited and revoked automatically.

### Secrets, zero trust and detection

Applications need passwords, keys and certificates to talk to each other. A **secrets vault** issues them at run time and rotates them, so they are never written into code or configuration files. **Zero trust** means no request is trusted just because it comes from inside the network; every call is authenticated and authorised. A **SIEM** collects logs from across the estate and raises alerts on suspicious patterns, and a security operations team investigates them.

## Failure modes

- **Flat networks,** where one compromised server can reach the core directly.
- **Standing administrator accounts** shared by teams, with no record of who did what.
- **Secrets in code** or configuration files that end up in a repository or a backup.
- **Alerts no one reads,** where monitoring exists but is not staffed or tuned.
- **Supplier blind spots,** where an incident at a service provider is not passed on quickly enough to meet reporting deadlines.

## When to use it, and when to avoid it

Every principle here applies to every bank; the question is depth. Put the strongest controls around what would hurt most: money movement, keys, customer data and administrator access. Avoid security measures that people work around, such as approval steps so slow that teams share credentials to meet a deadline. A control that is bypassed in practice gives false comfort.

## Questions for a design review

- If one application server is compromised, which systems can it reach?
- Who holds standing administrator rights today, and could that be replaced with just-in-time access?
- Where are keys and PINs handled, and does any application ever see them in clear?
- Where are application secrets stored, and how often are they rotated?
- Can an incident at a supplier be detected and reported to the regulator within the deadline?
