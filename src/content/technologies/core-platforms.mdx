## Why it matters

The core platform is usually a bank's largest single technology decision. It sets the product catalogue the bank can offer, how quickly it can change, which skills it needs and which vendor it depends on for the next decade or more. [Core banking system architecture](/architecture/cbs/) explains what a core does; this page covers the products.

### Deployment models

A common pattern is for a large bank to run its core on-premises, in its own data centres, with a disaster-recovery site. Some platforms are also offered hosted by the vendor or a partner, or as software as a service. Smaller banks often share a platform. <Fact id="ibcc-cbs" show="claim" /> Any arrangement where a third party runs the core brings RBI's outsourcing rules into play: <Fact id="rbi-md-it-outsourcing-2023" show="claim" />

### Database dependence

Established cores were built on large commercial relational databases, and their performance, licensing and skills needs follow from that choice. Some vendors now support open-source databases for parts of the platform. <Fact id="edb-finacle-2019" show="claim" />

## How to choose

Banks usually weigh six things:

- **Functional fit:** the products the bank sells today and expects to sell, including Indian requirements such as priority-sector tagging, regulatory returns and connections to Indian payment rails.
- **Architecture:** whether the platform can run modules independently, expose APIs and cope with round-the-clock payments without long batch windows.
- **Proven scale:** reference customers of a similar size, checked directly rather than taken from brochures.
- **Total cost:** licences, hardware, database, implementation partner, upgrades and the in-house team, over ten years rather than one.
- **Skills and partners:** how many people in the Indian market know the platform, and how many implementation partners support it.
- **Exit:** how data would be extracted and moved if the relationship ended.

## Pitfalls

- **Customising instead of configuring.** Code changes to the vendor's product make every later upgrade slower and riskier.
- **Buying for the demo.** A platform chosen on user-interface screens rather than on batch performance, APIs and data model disappoints later.
- **Underestimating data migration,** which is usually the longest and riskiest part of the programme.
- **Ignoring the database bill.** Database licences and specialist skills can rival the platform's own cost.
- **No exit plan,** leaving the bank unable to leave even when the relationship is failing.

## Questions to ask a vendor

- Which banks of our size run this version today, and can we speak to them without you present?
- How long does end of day take at our projected volumes, and what runs during it?
- Which functions are exposed as APIs, and which only through screens or files?
- How is a new product launched: configuration, scripting or code change?
- How do we extract all our data, in what format, if we leave?
