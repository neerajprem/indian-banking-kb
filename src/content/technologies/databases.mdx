## Why it matters

A bank's database is where money actually lives. If it loses a confirmed transaction, or lets two withdrawals both succeed against a balance that covers only one, the error is real money. Most other design choices in a bank can be revisited. The database behind the ledger rarely can.

## What money needs from a database

The four properties known as **ACID** matter most:
- **Atomicity:** a transfer's debit and credit both happen or neither does.
- **Consistency:** rules such as "balance may not go below the overdraft limit" always hold.
- **Isolation:** concurrent transactions do not see each other's half-finished work.
- **Durability:** once confirmed, a transaction survives a crash.

Relational databases were built for exactly this, which is why ledgers run on them.

### Clustering and replication

A single database server is a single point of failure. **Clustering** runs several servers so that one can take over from another. **Replication** copies data to other servers or sites, synchronously (no loss, slower writes) or asynchronously (faster, small possible loss). RBI expects critical systems to aim for no loss at all: <Fact id="itgrc-near-zero-rpo" show="claim" /> Replication is not a backup, though: a deleted table is deleted everywhere. <Fact id="itgrc-backup-restore" show="claim" />

## How to choose

Start from the consistency the data needs, not from the technology. Balances, postings and anything else that must never be wrong belong in a relational database with full transactions. Data that is read far more than written, such as reference data or a customer's recent transactions for an app screen, can be cached. Data whose shape changes often and which does not move money, such as onboarding forms, can suit a document store. High-volume append-only data, such as events and logs, suits stores built for writes.

## Pitfalls

- **Treating a cache as the truth,** for example approving a payment against a cached balance.
- **Assuming replication is a backup.** Mistakes replicate too.
- **Choosing a store for its speed** and discovering later that it cannot run a multi-record transaction.
- **Migrating engines without checking behaviour,** such as differences in how dates, rounding or locking work.
- **Long-running reports on the ledger database,** slowing customer transactions.

## Questions for a design review

- Which data here must never be wrong, and which store holds it?
- What isolation level do money-moving transactions run at?
- If the primary database fails now, how much data is lost and who reconciles it?
- When was a backup last restored and checked?
- Which reads could move to a cache or replica, and how stale may they be?
