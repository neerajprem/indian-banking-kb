## Why it matters

Banks now build many of their channel, payment and integration services as small applications that change often. Containers let each one be packaged once and run the same way on a laptop, in testing and in production. An orchestration platform then runs hundreds of them, restarts failures, scales with load and rolls out changes gradually. For a bank, the prize is faster, safer change; the cost is a platform that must itself be run to a very high standard.

## GitOps and infrastructure as code

**Infrastructure as code** defines servers, networks and clusters in files kept in version control, so an environment can be rebuilt exactly. **GitOps** extends that to applications: the Git repository holds the desired state of every cluster, and an agent keeps the live cluster matched to it. Every change is a reviewed commit with an author and a timestamp, which is also an audit trail.

This matters for resilience. RBI expects the primary and DR sites to match: <Fact id="itgrc-dc-dr-identical" show="claim" /> Defining both sites from the same code is the most reliable way to keep them identical.

## What regulated workloads add

- **Separation:** production isolated from development and testing, with separate clusters or strictly controlled namespaces.
- **Image control:** only images built by the bank's pipeline, scanned for vulnerabilities and signed, may run in production.
- **Policy enforcement:** admission rules that block privileged containers, missing resource limits or unapproved registries.
- **Secrets:** credentials supplied at run time from a vault, never baked into images.
- **Evidence:** logs of who deployed what, when, and with which approval.
- **Outsourcing:** where a provider runs the platform, <Fact id="rbi-md-it-outsourcing-2023" show="claim" />

## How to choose

Start with a supported distribution or a managed service rather than assembling upstream Kubernetes by hand, unless the bank has a strong platform team. Standardise on one deployment method, usually GitOps, across all teams. Move stateless services first; keep databases and other stateful systems on proven infrastructure until the platform has shown it can run them reliably.

## Pitfalls

- **Treating the platform as a project,** not a product that needs a permanent team.
- **Manual changes in production** that drift from what Git says.
- **Stateful systems moved too early,** before backup, failover and upgrades are proven.
- **Missing resource limits,** so one service starves others on the same nodes.
- **Unpatched base images** carrying known vulnerabilities into production.

## Questions for a design review

- Can this environment be rebuilt from code alone, and when was that last done?
- Which images may run in production, and how is that enforced?
- Where do this service's secrets come from?
- Are the primary and DR clusters defined from the same code?
- Who owns the platform, and how are its upgrades scheduled and tested?
