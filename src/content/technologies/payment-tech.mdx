## Why it matters

Payments are where precision and security matter most, and where much of the technology is not the bank's choice. Networks and regulators set message formats, security rules and authentication requirements, and every participant must implement them exactly. [Payment system architecture](/architecture/payments/) explains the model; this page covers the technology that implements it.

## Message standards

**ISO 8583** is the long-standing format for card authorisations: compact, fast and built around numbered fields such as amount, merchant type and response code. **ISO 20022** is a richer standard with structured data about the parties and the purpose of a payment. That structure helps screening, reconciliation and fraud detection. Payment engineers spend much of their time translating between formats and validating every field.

## Keys, PINs and HSMs

Payment security rests on keys. PINs are encrypted at the point of entry and verified inside hardware security modules, so no application ever sees a clear PIN. Keys are organised in hierarchies: a small number of master keys protect the keys that protect data. They are changed on schedules, and handling them needs several people present, so no one person can misuse them.

## Tokens instead of card numbers

<Fact id="cof-2022" show="claim" /> A token works only for the merchant or device it was issued for, so a breach at one merchant does not expose usable card numbers. Tokenisation services, run by card networks and issuers, create tokens, map them back to cards for authorisation and manage their lifecycle when cards expire or are replaced.

Every component in the path, such as message parsing, fraud scoring, HSM operations and the core posting, has a share of a tight time budget. A slow HSM or an overloaded fraud engine shows up to customers as failed payments.

## How to choose

Most choices here are about implementation quality rather than technology selection: follow each network's specification exactly, certify early, size HSMs and tokenisation services for peak rather than average load, and keep payment components separate from the rest of the estate to limit what falls under card-security rules.

## Pitfalls

- **Loose message validation,** letting malformed fields through to downstream systems.
- **HSM capacity sized for average load,** failing on festival or salary days.
- **Card numbers surviving in logs,** test data or analytics copies.
- **Authentication added as an afterthought,** creating extra steps that customers abandon.
- **Specification drift,** when a network updates its rules and one component is not upgraded.

## Questions for a design review

- Which message standards does this system parse, and how strictly is each field validated?
- Where are keys and PINs handled, and does any system see them in clear?
- Could a card number appear in any log, file or database outside the tokenisation service?
- Which authentication factors does each journey use, and which is dynamic?
- What is the time budget for each step in the payment path, and what happens when one is exceeded?
