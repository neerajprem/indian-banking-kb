## Why it matters

Banks connect hundreds of systems. Calling each one directly and waiting for an answer makes every system as slow and as fragile as the slowest one it calls. Messaging lets a system hand off work and carry on, while another system picks it up when it can. It is how banks absorb peaks, decouple teams and feed real-time fraud and analytics.

## Queues and logs

A **queue** holds messages until a consumer takes them, and each message goes to one consumer. It suits distributing work: "send this SMS", "generate this statement". A **log** keeps messages in order for a set time, and any number of consumers read it at their own pace, each keeping its own position. It suits event streams, audit trails and feeding several systems from one source. [Event-driven architecture](/architecture/event-driven/) covers the design patterns.

## How to choose

Ask three questions. **Does more than one system need the same message?** If so, a log. **Must messages stay in order?** If so, which ones: usually all messages for one account or one payment, which a partitioned log can keep together. **How long must messages be kept?** A queue deletes a message once handled; a log can keep days or weeks, so a new consumer or a fixed bug can replay history.

## Handling repeats safely

Almost every messaging system can deliver a message more than once, for example after a timeout and retry. For money, a repeated message must never move money twice. The usual answer is an idempotent consumer: it records each message's unique key and ignores keys it has already processed.

<CodeBlock lang="ts" title="An idempotent consumer (illustrative)" code={`
async function handle(msg: PaymentMessage) {
  // The key comes from the sender and is the same on every retry.
  const seen = await db.processed.find(msg.idempotencyKey);
  if (seen) return seen.result; // already done: return the same answer

  return db.transaction(async (tx) => {
    const result = await postToLedger(tx, msg);
    await tx.processed.insert({ key: msg.idempotencyKey, result });
    return result;
  });
}
`} />

<Callout type="risk" title="Exactly-once has limits">
  <p>Products that promise exactly-once delivery keep that promise inside their own boundary. The moment a message causes a change in another system, such as a core ledger, the application still needs its own idempotency check.</p>
</Callout>

## Pitfalls

- **Assuming exactly-once delivery** and skipping idempotency checks.
- **Hot partitions,** where one busy key, such as a large merchant, overloads a single partition.
- **Unbounded retries** that hammer a failing system; use back-off and a dead-letter queue for messages that keep failing.
- **Silent consumer lag** with no alert.
- **Changing message formats** without versioning, breaking consumers.

## Questions for a design review

- What is the key for each message, and does every consumer check it?
- Which messages must stay in order, and what partition key guarantees that?
- Where do messages go after repeated failure, and who looks at them?
- How far can each consumer fall behind before an alert fires?
- How long are messages kept, and does that respect data retention rules?
